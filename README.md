# 明堂图 · 三维经穴骨度定位模型 v1.0

> 361 个经穴，每一个都标出它凭什么站在那个位置。

### ▶ 在线查看：https://zgch028.github.io/mingtang-3d/

（GitHub Pages 托管，国内访问偏慢，首次打开可能要等十几秒；急的话直接下 `index.html` 双击，一样的效果。）


一个单文件的三维人体经穴模型。Three.js 内联、无依赖、无构建，双击 `index.html` 就能打开，断网也能跑。

「明堂」是经穴图的古称。孙思邈《千金要方》中有《明堂三人图》——仰人、俯人、侧人；本模型的正视 / 背视 / 侧视三档预设，就是这个传统的三维延续。

---

## 为什么做这个

常见的三维经穴模型，坐标大多是「等分插值」出来的：知道某经从肩走到手，就把中间的穴位均匀摊开。看起来整齐，但**没有一个位置站得住**——你无法回答「手三里凭什么在这里」。

这个模型换了个做法：**每个穴位的位置都要能反算回一句古法描述**（如「肘横纹下 2 寸」「平第 11 胸椎棘突下，旁开 1.5 寸」），再叠加骨性标志校核。算不出来的，就老实标成「示意」。

## 四级可信度

| 级别 | 含义 | 视觉 | 穴数 |
|---|---|---|---|
| **实定位** | 按骨度分寸或骨性标志算出，可复算、可校核 | 实心球 | **229（63.4%）** |
| 待重建 | 有寸数可抽，但缺对应骨性几何 | — | 0 |
| 近似 | 仅有段落约束 | — | 0 |
| **示意** | 落在体模没有几何的部位（手足末端 / 头面五官），只表大致区域 | 空心笼 | **132（36.6%）** |

229 穴的构成：四肢主干 92 + 脊柱组 53 + 胸肋 26 + 躯干旁开 43 + 肩带 12 + 骨盆 3。

跨级之间的经络连线画成**虚线**——它的意思是「这两端之间没有可信坐标，中间是直线硬接的」，不是真实走行。

## 边界（比精度数字更重要）

这一节请务必读完再看那个 63.4%。

1. **体模是简化的标准体模，不是真人扫描。**「实定位」指在该体模上按骨度分寸 / 骨性标志算得的位置——可复算、可校核，但**不是解剖测量值**。
2. **132 穴为示意级，不参与精度声明。**它们是把手足末端与头面部位画成大致区域，不用来取穴。
3. **掌跖骨与颅骨有意不建几何。**为几十个穴重造一整只手，性价比不如标成示意级；而把头做成一个球是有意的简化，硬做眼耳鼻口，只会把「不确定」包装成「精确」——这比诚实标示意级更糟。
4. **体模本身有已知比例偏差**：脊柱腰骶偏细、胸腹交界处有台阶、肩部收窄、髋部比腰细约 0.56 寸、下肢整体偏低约 8 寸。这些都记在工程报告里，未修（改一处要重算几十个穴）。
5. **有一处实定位穴位坐标重合**——阴陵泉（脾经）与曲泉（肝经）。已知、根因已定位、修法已备，**v1.0 决定不修**。理由与修法坐标都写在下文「可复跑校核」里。
6. **不用于临床取穴。**要精确取穴，请查 GB/T 12346《腧穴名称与定位》。

## 怎么用

- **拖拽**旋转，**滚轮**缩放
- **点击穴位**：看到定位描述、寸数换算、所属经脉与病候
- **左上勾选**：按经脉显隐
- **右上**：正视 / 背视 / 侧视 / 复位
- **只看已重建**：把示意级淡化到背景，专注 229 个实定位穴
- 琥珀编号表示该处有多个穴位重合，可点开选组内穴

## 可复跑校核

```bash
node verify/verify.cjs
```

零依赖——只用 Node 内置模块，不需要 `npm install`。它从 `index.html` 里抽出 361 穴坐标，现场重算 40 项校核，写出 `verify/verify_report.json`。

### 当前结果

| | 项数 | 通过 | 未通过 |
|---|---|---|---|
| 自算校核（任何人可跑） | 40 | 38 | **2** |
| 历史归档（七批求解当时的记录） | 78 | 78 | 0 |

**那 2 项是同一个缺陷**：**阴陵泉（脾经）与曲泉（肝经）坐标完全重合**，同为 `[0.0676, -0.4393, 0.065]`。同一缺陷触发两条断言（跨经重合、两两最近距离 ≥ 0.004 实测 0.0000），不是两个独立故障。

- **根因**：下肢求解表里曲泉的方位角被写成了阴陵泉的 150°。同段（膝横纹高度）四穴的方位角应为：阴陵泉 150°（胫骨内侧髁下缘）、膝关 165°、曲泉 **190°**（肌腱内缘）、阴谷 200°（肌腱之间）。
- **为什么 78 项归档没抓到**：那一条叫「**经内**不重合」，只查同一条经内部；这两个穴分属脾经与肝经，跨经，正好落在七批校核的夹缝里。
- **修法已备、未执行**：方位角 150° → 190°，坐标 → `[0.0599, -0.4433, 0.0214]`（距阴谷 0.49 寸、距膝关 1.21 寸），已通过轴点反解验证。完整步骤见 `verify_report.json` 的 `dispositions[0].fix_prepared.steps`。

### 为什么决定不修（作者判断，2026-11-03）

这一项本可以悄悄改掉。没改，是三个理由：

1. **v1.0 已定版公开。**改一个坐标会连带改文件 sha256 与版本号，而作品的立身之本是 229 穴的定位方法，不是这一个点。
2. **这 2 项 FAIL 留在公开报告里，是校核阈值没被松过的证据。**一份 40/40 全绿的清单，读者无从判断阈值是不是调到刚好能过；一份红着 2 项、每项写明根因与修法的清单，读者可以自己判断。
3. 界限要说清：这是「**记录诚实**」，不是「缺陷可以不管」。修法就在上面，谁要修都能修。

**读者实际会看到什么**：该处两个球叠为一个。界面把所有精确同坐标的穴位收成琥珀数字牌（此处「2」），点击牌面可选组内穴——所以阴陵泉与曲泉仍能分别点开查看，信息可达性没有受损，代价是多一步点击。这处重合也列在左侧「全部重合处清单」里。

> 处置登记写在 `verify_report.json` 的 `dispositions` 段，`summary.verdict` 仍是 `FAIL`（不改写成更好听的词），另给 `known_open: 2 / unexplained: 0`——让读者能一眼分清「作者已知并说明了的红」和「作者没管好的红」。

### 40 项和 78 项不是包含关系

- **40 项**从已发布数据现场重算，验的是「数据自洽」：点数、分级、单侧前提、间距、重合、包络、胸肋字段，以及界面横幅上的数字是否与数据一致。
- **78 项**是七个批次求解当时的记录，多数要靠未随仓库发布的中间数据才能复算（骨度锚点表、体模几何）。`verify_report.json` 的 `coverage` 段与每条的 `needs` 字段逐项写明了缺什么。

它验不了「穴位是否符合古籍」——那需要文献对照，脚本无能为力。**能证伪的才写成 check，不能证伪的写成 observation**，不参与通过率统计。一份只报喜的清单没有意义。

## 数据与方法

- 穴位数据 361 条（含左右对称前的单侧定义），源自原设计数据集
- 定位方法：骨度分寸法（十二经骨度）＋ 骨性标志（椎节表、十二对肋骨、肩胛冈与肩峰、锁骨、髂前上棘、耻骨联合）
- 分段寸长：横向 1 寸 = 0.0233；纵向脐上 1 寸 = 0.0158、脐下 1 寸 = 0.0200
- 渲染：Three.js r149（内联），单文件，无外部请求
